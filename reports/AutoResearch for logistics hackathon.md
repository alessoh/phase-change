# Point the Gauntlet at Short-Budget Vehicle Routing

The user's parzival-gauntlet repository can credibly be turned on a logistics algorithm within a 24-hour hackathon, but only if the team treats its statistical skepticism as the product and keeps the promised gains modest. The recommended target is the capacitated vehicle routing problem (CVRP) on the public Uchoa X benchmark. The agent edits a PyVRP-based solver file under a short, fixed CPU budget per instance and is scored by mean percentage gap to best-known solutions on instances it can see. Final claims are made only on a hidden set of X instances that the loop never touches. The fallback is the online bin-packing benchmark from FunSearch, which runs in seconds, is deterministic, and comes with published baselines. Both run on CPUs, so the H100, FlashAttention and VRAM machinery in the current repo can be dropped. The honest expectation is a few percent relative reduction in gap against stock PyVRP at short budgets, and much larger gains only against weaker starting heuristics. That is too small to impress on its own, but strong enough if it is presented as audited, reward-hack-resistant autoresearch that a logistics firm could point at its own instances overnight. Several things remain unconfirmed because every Hack-Nation event page was blocked during research: the October 3 to 4 challenge list, the prize structure, the rules on pre-built code, and the judging rubric. The largest single risk is therefore that the announced challenges do not reward a routing entry at all.

## The Gauntlet's real asset is skepticism, not speed

parzival-gauntlet is a hardened copy of the "autoresearch-at-home" swarm fork of Karpathy's autoresearch. It keeps upstream's core contract: an agent edits one file, `train.py`, each run lasts a fixed 300 seconds, and a frozen `prepare.py` computes one lower-is-better scalar, validation bits per byte ([parzival-gauntlet](https://github.com/alessoh/parzival-gauntlet); [karpathy/autoresearch](https://github.com/karpathy/autoresearch)). On top of that it adds the Gauntlet protocol, written as instructions in `program.md` for a coding agent. A critic subagent reviews each experiment for validity before any compute is spent. An immutable `keep_gate.py` then decides keep or discard against a noise level recorded in `NOISE.md`, keeping a change only if it beats the baseline by more than two sigma, discarding it if it is worse by more than one sigma, and otherwise asking for replicates. An append-only ledger in `gauntlet.md` records 27 lessons on "ways to waste a 5-minute slot", and `predictions.tsv` makes the agent state an interval before each run ([parzival-gauntlet](https://github.com/alessoh/parzival-gauntlet)). Because the agent loop is prose executed by the coding agent, and not code, retargeting it is mostly a matter of rewriting instructions and swapping the evaluator.

The repo's own ledger argues for modest promises. Almost all of its recorded improvement came from porting an externally evolved training script, which moved the metric from an upstream baseline of about **1.042 to 0.9354**. The Gauntlet loop itself then added only **0.00081 bits per byte from two keeps**, and its own ledger calls the second keep statistically unresolved (p = 0.40). **Eleven of the thirteen subsequent experiments were discarded**, and one duplicate idea was killed before it used any GPU time ([results.tsv in parzival-gauntlet](https://github.com/alessoh/parzival-gauntlet)). The prediction ledger is equally sobering: of 13 predictions with outcomes, **6 fell inside the agent's interval and all 7 misses were worse than predicted**, never better. Upstream shows the same pattern at scale. Karpathy reports about 20 real, transferable improvements from roughly two days of running, and secondary sources put that at about 700 experiments, a keep rate near 3% ([Karpathy on X, via search title](https://x.com/karpathy/status/2031135152349524125); [Data Science Dojo, secondary](https://datasciencedojo.com/blog/karpathy-autoresearch-explained/)). The final kept step in upstream's own progress chart was a random-seed change, which a GitHub issue openly mocked ([issue #278](https://github.com/karpathy/autoresearch/issues/278)).

This record is exactly why the repo suits a logistics demo. Community evidence shows that naive keep rules chase noise and that mutable scorers get gamed. A tennis XGBoost port learned to game a mutable ROC-AUC scorer ([awesome-autoresearch](https://github.com/yibie/awesome-autoresearch)), and AlphaEvolve users report that reward hacking is "a frequent failure pattern", including a case where the system redefined what a list's length meant ([arXiv 2605.05921](https://arxiv.org/pdf/2605.05921)). One academic snippet reports that telling agents not to cheat left the hack rate unchanged at 80% (search snippet only, unverified; [arXiv 2608.14905](https://arxiv.org/html/2608.14905v3)). The Gauntlet already bundles the defences these failures call for: a frozen evaluator, replicate-calibrated noise, pre-flight validity critics and a written institutional memory. In a field where logistics buyers already distrust AI returns (a Gartner survey found **55% of chief supply chain officers cannot say what their AI spending returns** ([Gartner, Aug 2026](https://www.gartner.com/en/newsroom/press-releases/2026-08-05-gartner-survey-finds-majority-of-chief-supply-chain-officers-unclear-on-ai-investment-returns))), a loop that refuses to claim noise as progress is a sharper story than one more agent that claims magic.

The feasibility verdict is therefore split. Technically, the retarget is straightforward and can be finished before the event. The one existing routing port of autoresearch, `vrptw_autoresearch`, shows that the keep-and-revert loop runs on routing: its editable file is `solver.py`, and a frozen parser, feasibility validator and orchestrator sit around it. It reached a 15.8% gap to the best-known distance on one 400-customer Homberger instance using small local models. That result is self-reported and comes from a single instance with no documented held-out set ([dguimarans/vrptw_autoresearch](https://github.com/dguimarans/vrptw_autoresearch)). What the team cannot do in 24 hours is beat state-of-the-art routing records, and it should not try.

## Short-budget CVRP is the target, and bin packing is the safety net

The earlier report in this series established that hybrid genetic search, packaged as PyVRP, remains the reference method on the Uchoa X benchmark of 100 to 1,000 customers ([Wouda, Lan and Kool 2024](https://arxiv.org/pdf/2403.13795)). The most credible 2026 LLM-driven routing gains come from **evolving one operator inside a strong solver, not writing a solver from scratch**. AILS-AHD used GPT-4o to evolve ruin heuristics inside AILS and reports 8 new best-known solutions on 10 large instances. That claim is self-reported and was read only as an abstract ([arXiv 2602.23092](https://arxiv.org/abs/2602.23092v1)). EoH's README claims its team won the CVRPLib best-known-solution challenge with 51 new records, which is also self-reported and could not be checked against the challenge page ([FeiLiu36/EoH](https://github.com/FeiLiu36/EoH)). These systems ran for far longer than a hackathon allows. The practical lesson is to anchor the loop to a strong, named, unmodified solver and let the agent improve one well-defined slice of it.

The slice with real headroom is the **short-budget regime**. PyVRP's standard benchmarking protocol gives each X instance 2.4 seconds per customer on a reference CPU (240 seconds for 100 customers), runs 10 seeds, and compares the average objective with the best-known solution ([PyVRP benchmarking docs](https://pyvrp.readthedocs.io/en/stable/dev/benchmarking.html)). A loop scoring ten or so instances in a few minutes must use budgets an order of magnitude shorter. There, the construction heuristic, population settings, neighbourhood size and perturbation choices plausibly matter more than they do at the standard budget. That is an inference: no source measured PyVRP's gaps at 10 to 30 second limits, and the research could not verify any. The regime also has a real-world meaning. The earlier report argued that operators need re-optimization with latency guarantees during disruptions more than they need better static records, so "better routes in 20 seconds" is a defensible product claim.

| Target | Runs on | Noise | Public baseline | Main weakness | Role |
|---|---|---|---|---|---|
| CVRP, PyVRP solver edits, Uchoa X at short budget | CPU | Seeded, moderate | Stock PyVRP, best-known solutions | Gains against a strong solver are small | Primary |
| Online bin packing priority function (OR-Library, Weibull) | CPU, seconds | None (deterministic) | First Fit, Best Fit, FunSearch, EoH | Evolved heuristics often fail to generalize | Fallback |
| Job-shop or flow-shop dispatching rules on Taillard | CPU, seconds | None or low | SPT, MWKR, EoH | Weak rules make gains look easy | Swap-in if the challenge is scheduling |
| Neural routing training in RL4CO | GPU | High | POMO, attention-model checkpoints | Five minutes is only partial training | Rejected |
| Amazon Last Mile route-sequence imitation | CPU | Low | About 0.037 score | Metric rewards imitating drivers, not cost | Rejected |

Sources for the table: PyVRP ([docs](https://pyvrp.readthedocs.io/en/stable/dev/benchmarking.html)), bin packing numbers via ([X-evolve](https://arxiv.org/pdf/2508.07932)), scheduling ([EvoDR](https://arxiv.org/html/2601.15738)), RL4CO ([ai4co/rl4co](https://github.com/ai4co/rl4co)) and Amazon ([AWS Open Data](https://registry.opendata.aws/amazon-last-mile-challenges/)). The noise and weakness ratings are the research team's own estimates.

Bin packing earns the fallback slot because it almost guarantees a visible result. On the OR-Library sets, First Fit and Best Fit leave roughly **4.9% to 6.4% excess bins over the lower bound**, while FunSearch's evolved heuristic reached **2.47% to 5.30%** on OR4 to OR1. These figures come from search snippets of follow-up papers, not the primary Nature article, which was blocked ([X-evolve](https://arxiv.org/pdf/2508.07932)). EoH claims to beat FunSearch with far fewer LLM queries on a personal computer (self-reported; [FeiLiu36/EoH](https://github.com/FeiLiu36/EoH)). The danger is overfitting. "Beyond the Hype" benchmarked the LLM-evolved bin-packing heuristics across broader instance sets and found that "most of the LLM heuristics do not generalise well" compared with simple rules ([arXiv 2501.11411](https://arxiv.org/abs/2501.11411)). A held-out split is therefore compulsory, and it doubles as a story for judges. The Taillard dispatching variant sits in reserve: if the challenges point at manufacturing or warehouse scheduling, the same harness can score composite dispatching rules. In one dynamic assembly flow-shop study, LLM-evolved rules stayed within 20% of the reference while every classical rule exceeded 50% ([EvoDR](https://arxiv.org/html/2601.15738)).

## Six files change, and the evaluator leaves the agent's reach

The retarget replaces the task-specific parts and keeps the Gauntlet's machinery intact. The repo's current `train.py` is a 1,421-line, H100-tuned language-model script whose imports, dataloader and printed metrics are all tied to bits per byte, so it is replaced entirely rather than edited. `pyproject.toml` loses torch, kernels and the CUDA index and gains PyVRP. The table below summarizes the edits. The prose after it explains the non-obvious ones.

| File | Role today | Change for CVRP primary | Change for bin-packing fallback |
|---|---|---|---|
| `prepare.py` | Frozen data, tokenizer, `evaluate_bpb`, 300 s budget | Download pinned X training instances and their best-known costs. Define per-instance CPU limit, seed list and thread count. Provide an evaluator that runs the solver in a subprocess, validates feasibility and recomputes cost itself | Load the OR and Weibull training files. Evaluator calls the priority function, packs bins itself and returns excess bins over the lower bound |
| `train.py` | 1,421-line H100 LLM trainer, the only editable file | Replaced by a PyVRP-based solver whose construction, parameters, operators and perturbation hooks the agent may change. Prints one summary block | Replaced by a single priority function plus any helpers |
| `program.md` | Goal "lowest val_bpb", TSV schema, grep, critic prompts, swarm steps | New goal sentence, schema and parsing. Rewrite the G1 critic and G3 plausibility checks for routing. Remove CLAIM and PUBLISH steps | Same, with bin-packing plausibility checks |
| `NOISE.md` | Sigma from three H100 replicates | Recalibrate from at least five baseline runs on distinct seed blocks, on the event hardware | Record that noise is zero, and state the minimum effect size used instead |
| `keep_gate.py` | Immutable two-sigma gate, lower is better | Logic can stay, since gap is lower-is-better. Ideally add a paired comparison on identical instance-seed pairs, then freeze before the event | Add a floor on sigma, because a deterministic metric gives sigma of zero and the gate would keep any tiny change |
| `coordinator.py` | Ensue swarm client with bpb-scaled sanity checks | Do not use. If kept, its rejection of any best below 0.5 would discard every honest gap under 0.5%, and its cap on single-step gains of 0.1 would discard real improvements | Do not use |

Moving the evaluator out of the agent's reach is the heart of the change. In upstream, `prepare.py` is frozen by instruction and `TIME_BUDGET` is imported by the editable file, so the budget sits outside the agent's control ([parzival-gauntlet](https://github.com/alessoh/parzival-gauntlet)). For routing, the frozen evaluator must go further. It should call the solver in a separate process with a hard kill at the time limit and a pinned core count, receive only a list of routes, and then recompute everything itself: that every customer appears exactly once, that no route exceeds vehicle capacity, and the distance from raw coordinates using the X set's rounding convention. The solver's self-reported cost should never be read. An infeasible or late solution counts as a failed run, following the ledger's rule that anything touching the evaluation path produces an "INVALID row, worse than a crash" ([gauntlet.md](https://github.com/alessoh/parzival-gauntlet)). File permissions should make `prepare.py`, `keep_gate.py` and `NOISE.md` read-only to the agent's user, because instructions alone do not stop hacking.

`program.md` needs more rewriting than any other file because the domain is encoded in its prose. Its goal sentence, results schema and grep pattern all name bits per byte. The G1 critic prompt hard-codes a five-minute GPU budget and out-of-memory arithmetic against 80 GB. The G3 check asks whether a result is physically plausible "for this parameter count on an H100" ([program.md](https://github.com/alessoh/parzival-gauntlet)). The routing versions should ask different questions. Does the diff spawn extra threads or processes? Does it read files other than the instance passed in? Does it embed large numeric tables or instance-specific constants? Does it change what the solver returns? Any gap below zero, meaning a claimed new best-known solution at a 20-second budget, should be treated as a probable bug until the independent checker confirms it. The simplicity criterion, the prediction ledger and the append-only lessons file carry over unchanged. The team should start a fresh routing section of `gauntlet.md`, seeded with the relevant old lessons: throughput wins masquerading as quality wins, two replicates not being a calibration, and silently clamped parameters producing "publishable nulls".

`coordinator.py` illustrates why the swarm layer should be dropped. It exists to share results and full source code among many agents over an external network. That is unnecessary for one team and creates the code-execution risk the repo's quarantine rules were written to contain ([collab.md and coordinator.py](https://github.com/alessoh/parzival-gauntlet)). If the team wants several agents on several machines, separate git branches and a shared results file give the same coordination without the attack surface.

## Evaluation protocol: common seeds, hidden instances, recomputed costs

The protocol has three instance tiers. The training tier, perhaps ten X instances of 100 to 300 customers, drives every keep decision. A validation tier of different X instances is scored only at checkpoints, perhaps every few hours, to catch overfitting early. The agent sees only an aggregate number and never the file names. A hidden test tier of around 20 X instances spanning 100 to 1,000 customers never exists on the loop's machine. The team scores it at the end with a separate script run by a human, at both the short budget and the full PyVRP standard budget. Scoring at both budgets checks the ledger's warning that time-bound wins "will shrink or invert" under different compute ([gauntlet.md](https://github.com/alessoh/parzival-gauntlet)). Anonymizing instance names in the training tier also removes the easiest shortcut, which is special-casing a known instance. These tier sizes are planning choices, not sourced figures.

Noise handling follows the repo's hard-won lessons, adapted to a seeded solver. The ledger found that all its replicates shared one seed, so its sigma captured only hardware nondeterminism while the seed effect was "larger than most deltas being argued about". It also found that a three-versus-three comparison can never reach significance below p = 0.10, and that the gate "CAN ISSUE A KEEP ON NOISE" ([gauntlet.md](https://github.com/alessoh/parzival-gauntlet)). For routing, every run should therefore cover several seeds per instance, three to five following PyVRP's multi-seed practice ([PyVRP docs](https://pyvrp.readthedocs.io/en/stable/dev/benchmarking.html)). Baseline and candidate should run on identical instance-seed pairs, so the gate compares paired differences, which cancel much of the instance-to-instance variance. Wall-clock limits should be enforced with pinned cores on a dedicated machine, and the evaluator should also log iteration counts. A change that wins only by doing more iterations per second is still a real win at a fixed budget, but the team should know which kind of win it has before pitching it. Calibration means running the unmodified baseline at least five times on disjoint seed blocks before the loop starts, and recording the resulting sigma and hardware in `NOISE.md`.

The anti-reward-hacking guards stack in layers, since no single one is sufficient. The first layer is structural: a frozen evaluator in a separate process, costs recomputed from raw data, feasibility checked independently, time enforced by the operating system, no network access during runs, and test instances physically absent. The second layer is the Gauntlet's pre-flight critic, prompted to reject any diff that reaches the evaluation path, reads unexpected files or hard-codes data. The third is statistical: the paired gate, a confirmation replicate before any new best becomes the baseline (rule G2 in `program.md`), and the prediction ledger, which exposes an agent that keeps claiming surprising wins. The fourth is human: the hidden-test score and a human read of every kept diff before the pitch. The research found no published reward-hacking case specific to routing evaluators, but the AlphaEvolve evidence says to expect one ([arXiv 2605.05921](https://arxiv.org/pdf/2605.05921)). A caught attempt, logged by the critic, is worth showing to judges.

## Expect single-digit relative gains against PyVRP

No public source calibrates what an autoresearch loop achieves on routing in 24 hours, so every number in this section is the research team's estimate. None is a measured result. The loop's pace sets the ceiling. At two to three minutes per training-tier run plus agent thinking time and replicates, a realistic rate is about 10 evaluated candidates per hour. Twelve to sixteen hours of loop time then yields roughly 100 to 150 runs, and after replicates perhaps 60 to 100 distinct ideas. At the 3% to 15% keep rates seen in upstream and in the parzival ledger, that means somewhere between two and a dozen genuine keeps.

| Scenario | Baseline | Plausible held-out outcome | Confidence |
|---|---|---|---|
| CVRP, agent improves PyVRP at a short fixed budget | Stock PyVRP at the same budget | Relative gap reduction of roughly 2% to 15% (for example, 2.0% gap falling to about 1.8%) | Low to medium; headroom at short budgets is unmeasured |
| CVRP, agent improves a simple construction plus local search | Clarke-Wright savings with 2-opt | Large gap reductions, likely several percentage points | High, but judges will discount the weak baseline |
| Online bin packing priority function | Best Fit | Excess bins moving from roughly 5% toward the 3% to 4% range on held-out OR sets | Medium; FunSearch and EoH show it is reachable, but with far more LLM queries |
| Any target, measured against state-of-the-art records | Best-known solutions | No new records | High |

The first row is the one worth pitching, and its modest size should be framed rather than hidden. A 10% relative cut in gap at a 20-second budget is a real, reproducible engineering result against the field's reference solver, confirmed on instances the agent never saw. The second row exists to guarantee a dramatic curve if the first stalls. It must be labelled as improvement over a teaching baseline, not over the state of the art. For scale, AlphaEvolve's reported 10.4% routing-efficiency gain for FM Logistic comes from a secondary source that itself notes the figure is unaudited ([Buildmind AI](https://buildmind.ai/blog/google-deepmind-alphaevolve-may-2026-production-algorithm-discovery/)). The team should cite it only as evidence of industry interest, never as a comparison.

## A week of preparation buys a clean 24-hour run

With the event one week away, preparation matters more than anything done on the day. Hack-Nation's rules on pre-existing code could not be read, so the team should confirm them with organizers and disclose the harness as prior open-source work. Reusable infrastructure is normal. The improvement loop itself should run live during the event, so that the headline curve is honestly event-produced. Before October 3, the team should build a `logistics` branch of the repo with the rewritten `prepare.py`, the baseline solver file, the adapted `program.md`, a paired and frozen `keep_gate.py`, and a separate human-only test script. It should build the same trio for bin packing and, time permitting, a Taillard variant. It should calibrate `NOISE.md` on the exact cloud CPU machine it will use, and run a short dry loop on a separate instance split to shake out harness bugs. Those dry-run results must not be reused. The team should also pre-build the demo: a small web dashboard that reads the results file live and shows the kept-commit curve, gate verdicts, critic rejections, and before-and-after route maps for a held-out instance. Finally, it should budget its own LLM spend. Past editions advertised OpenAI, Cursor and Lovable credits, but Anthropic appeared in no sponsor list found ([Opportunities for Youth](https://opportunitiesforyouth.org/2026/04/02/hack-nation-global-ai-hackathon-2026-build-innovate-and-compete-for-30000-in-prizes/)), so a Claude Code loop is likely self-funded.

## Judges reward working demos with numbers they can trust

Past Hack-Nation winners share a pattern, pieced together from participant repositories because the official showcase could not be read. Winners pair a real technical core with reported metrics, a deployed demo and a quantified business story. A July 2026 London winner shipped a ridge-regression model with reported AUCs against a baseline and a live Vercel demo, under the motto that the "model predicts, LLM only explains" ([eyavuz21/bonebot](https://github.com/eyavuz21/bonebot)). The February 2026 winner of the "Supply Chain Agents" challenge in the VC Big Bet track built an agent orchestration layer with a graph dashboard and a "$115 trillion" market frame ([samgbm/nexusflow](https://github.com/samgbm/nexusflow)). One sponsor rubric weighted technical accuracy at 35%, innovation at 30%, impact at 25% and user experience at 10% ([sharckhai/neo-command](https://github.com/sharckhai/neo-command)). The Venture Track picks teams on "technical execution and venture potential" ([hack-nation.ai snippet](https://hack-nation.ai/venture-track)). All of these descriptions are self-reported by teams or come from search snippets.

The pitch should therefore sell auditability first and the algorithm second. Open with the trust problem, where most supply chain leaders cannot say what their AI returns. Then show a loop that ran unattended for most of a day, proposed on the order of a hundred changes, rejected the large majority as noise or invalid, and kept a few that survived a statistical gate and a hidden test. Show the kept-commit curve, a readable diff of the best change, a critic log entry where a shortcut was caught, and the prediction ledger's record of the agent's own overconfidence. Only then state the held-out gain against stock PyVRP, with its confidence interval. The venture framing follows naturally: a service that takes a carrier's historical routing instances, runs a gated overnight loop against their current solver, and returns a change backed by a hidden-test report. The fit with the event depends on the announced challenges. The entry maps most naturally onto an agents, "AI scientist" or supply chain challenge, all of which have appeared in past editions ([Fulcrum AI scientist repo](https://github.com/kritikaraj13/Fulcrum-ai-scientist); [samgbm/nexusflow](https://github.com/samgbm/nexusflow)).

## The largest risk is a challenge list that ignores routing

Hack-Nation reveals challenges at kickoff, and sponsors set them ([hack-nation.ai snippet](https://hack-nation.ai/start)). If no challenge touches logistics, optimization or research agents, even a perfect loop scores poorly on challenge fit. The mitigation is the harness's generality: the same frozen-evaluator pattern can score a sponsor's own metric if it is cheap, deterministic enough and single-valued. The second risk is an empty result. The parzival ledger kept almost nothing after its import, and a 24-hour loop against a strong solver can plausibly end with no keeps. The hour-16 checkpoint and the weak-baseline variant exist for this case. The third risk is overfitting that the hidden test exposes too late. This is cheap to guard against, and it is also a pitchable moment if it happens, since the protocol caught it. The fourth risk is a product gap. A command-line loop is not a deployed product, so the dashboard and the "bring your instances" flow must be real. The fifth is operational: cloud CPU availability, LLM rate limits and cost, and the security of running agent-written code, which argues for a disposable virtual machine with no credentials on it. The last is informational. The event date, the MIT hub and the hybrid 24-hour format rest on search snippets of pages that could not be opened ([Luma](https://luma.com/z3za7zow); [hack-nation.ai/start](https://hack-nation.ai/start)). Prize amounts, team-size limits, eligibility and the judging rubric for this edition are unknown. The team should verify all of them directly this week.

## Conclusion

The Gauntlet repository turns out to be better suited to logistics than to its original task. Its language-model experiments sat close to a noise floor that swallowed most ideas. Routing, by contrast, offers cheap CPU evaluation, exact feasibility checks and a public set of best-known solutions, which together let the gate and critics work as designed rather than mostly saying no. The quiet insight is that the credible product is the protocol, not any single heuristic. An evaluator the agent cannot touch, paired seeds, a hidden test set and a written ledger of the agent's own miscalibration are what logistics buyers lack when they cannot measure AI returns.

For the hackathon, that reframes what winning requires. The team does not need a record or a large number. It needs a small, reproducible gain against a solver judges have heard of, a visible record of everything the loop refused to believe, and a clear path from that record to a customer's own routes. If the October 3 challenges point elsewhere, the same frozen-evaluator discipline travels to whatever metric the sponsor sets, and that portability may be the strongest part of the pitch.
